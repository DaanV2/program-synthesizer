# Project format

A synth project is a directory with a spec file and a `data/` folder. Every
file is plain text, so a project can be written by hand, generated by a
script or kept in git.

```text
fullname/
  spec.yaml              the types (or spec.json)
  data/
    train/
      in/<name>.json     input of example <name>
      out/<name>.json    expected output of example <name>
    holdout/
      in/<name>.json
      out/<name>.json
```

`synth init` creates this layout. Commands find the project by looking for
`spec.yaml` or `spec.json` in the `--project` directory (default: the
current one) and then in each parent directory, so they work from anywhere
inside the project.

Git does not store empty directories. A freshly cloned project without
examples may have no `data/` folder at all; that is fine, synth creates the
folders when it writes the first example.

## spec.yaml

```yaml
name: full-name
description: Join first and last name; flag adults
input:
  first: string
  last: string
  age: int
output:
  fullName: string
  isAdult: bool
options:
  float_tolerance: 1e-9
  targets: [go, rust]
```

| Key | Required | Meaning |
| --- | --- | --- |
| `name` | yes | Project name, a non-empty string. |
| `description` | no | Free text: what the function should do. |
| `input` | yes | The parameters of the function, as a record: parameter name to type. At least one. |
| `output` | yes | The return type. Any type: a scalar, a list or a record. |
| `options.float_tolerance` | no | A number >= 0: how far a float output may be from the expected value and still count as equal. Unset means 0 (exact). Stored and validated today; the search will use it when it exists. |
| `options.targets` | no | Back ends to generate code for, any of `go`, `rust`, `c`. `synth init` writes `[go]` unless told otherwise. Code generation does not exist yet. |

Unknown keys are an error, so typos do not go unnoticed. Comments are
allowed; `synth config` keeps comments on keys that still exist when it
rewrites the file, but drops blank lines.

Edit the file by hand or with [`synth config`](cli/synth_config.md), which
uses dotted keys such as `input.age` and `options.targets`.

### spec.json

A project may use `spec.json` instead. It has the same keys, and types are
written as JSON strings and objects:

```json
{
  "name": "sum",
  "input": {"a": "int", "b": "int"},
  "output": "int",
  "options": {"float_tolerance": 0.001}
}
```

Lists of records are written as one-element arrays: `"orders": [{"id": "int"}]`.
Field order is kept, as in YAML. `synth config` writes changes back as JSON.
`synth init` always creates `spec.yaml`. If a directory has both files,
`spec.yaml` is used and `spec.json` is ignored.

## Types

| Type | spec.yaml | JSON value in example files |
| --- | --- | --- |
| integer | `int` | a whole number that fits in 64 bits: `42`, `-7` (not `42.0` or `4.2e1`) |
| floating point | `float` | any JSON number: `2.5`, `3`, `1e-3` |
| boolean | `bool` | `true` or `false` |
| string | `string` | `"text"` |
| list | `list<T>` or `[T]` | an array whose items are all `T`, possibly empty |
| record | a mapping `{name: T, ...}` | an object with exactly these keys |

`null` is never a valid value.

### Lists

`list<int>` and `[int]` mean the same. Lists nest: `list<list<int>>` or
`[[int]]`.

A list of records must use the bracket form, because `list<{...}>` is not
valid YAML:

```yaml
input:
  orders: [{id: int, total: float}]
```

(`synth config set` and `synth init --input` accept `list<{id: int}>` as a
shorthand and store it as `[{id: int}]`.)

### Records

A record is a YAML mapping, written as a block or inline:

```yaml
input:
  customer:
    name: string
    vip: bool
  orders: [{id: int, total: float}]
output: list<int>
```

Field and parameter names must be identifiers: letters, digits and `_`, not
starting with a digit (`first_name`, not `first-name`), so they work in
every target language. A record needs at least one field, and names must be
unique within it.

`input` is always a record: each field is one parameter. `output` can be a
record too, in which case the function returns a struct.

### Field order

The order of fields in the spec matters, even though JSON objects are
unordered:

- The order of the `input` fields is the order of the generated function's
  arguments.
- The order of a record output is the order of the generated struct's
  fields.
- synth writes example files with fields in spec order, so they read the
  same way as the spec.

Example files themselves may list keys in any order. Reordering fields
(`synth config move`) never breaks examples.

## Example files

An example is a pair of files with the same name in the same split:
`data/train/in/turing.json` holds the input and `data/train/out/turing.json`
the expected output.

The input file is a JSON object with one key per input parameter:

```json
{
  "first": "Alan",
  "last": "Turing",
  "age": 41
}
```

The output file is a JSON value of the output type. For `output: list<int>`
that is just an array:

```json
[1, 2]
```

Rules:

- Names may contain letters, digits, `-`, `_` and `.`. Treat names as case
  insensitive: `Foo.json` and `foo.json` are the same file on Windows and
  macOS, and `data import` refuses an import that contains both.
- Only files ending in `.json` count. Other files and subdirectories in
  `in/` and `out/` are ignored.
- Files must be UTF-8 JSON without a byte order mark (see
  [getting-started.md](getting-started.md#from-files-works-in-every-shell)
  for the PowerShell trap).
- Names are unique per split. `train/001` and `holdout/001` are two
  different examples.
- `synth data add` and `synth data import` name examples `001`, `002`, ...
  unless a name is given (or, for folder imports, taken from the file name).
  Numbering continues after the highest number in the split.

synth writes example files with two-space indentation, record fields in
spec order, lists of scalars on one line and numbers exactly as given
(`2.50` stays `2.50`). You can also write the files yourself, with any
formatting.

## Validation

`synth data validate` checks the whole project and prints every problem it
finds. Here is a project with input
`{customer: {name: string, vip: bool}, orders: [{id: int, total: float}]}`
and output `list<int>`, with four problems:

```text
data/train/in/badtype.json: input.orders[1].id: expected int, got string
data/train/in/broken.json: unexpected EOF
data/holdout/out/orphan.json: no matching input in in/
contradiction: .../orders/data/train/in/ok.json and .../orders/data/holdout/in/same.json have the same input but different outputs

ERROR

found 4 problem(s).
```

What is checked:

1. **Pairs.** Every `in/` file has an `out/` file of the same name and vice
   versa.
2. **JSON.** Every file holds exactly one JSON value.
3. **Types.** Every value matches the spec. Errors give the path into the
   value, such as `input.orders[1].id`. Typical messages:

   ```text
   input.age: expected int, got string
   input.n: expected int, got 1.0
   input.x: expected float, got null
   input: missing field "age"
   input: unexpected field "y"
   output.isAdult: expected bool, got number 1
   ```

4. **Contradictions** (below).

`synth data add` and `synth data import` run checks 2 and 3 on each new
example before writing it, and `synth config set` re-checks all examples
after a type change.

The spec itself is checked whenever a command loads it. Real error messages
for broken specs:

```text
.../spec.yaml: line 3: unknown type "integer" (want int, float, bool, string, list<T>, or a mapping for a record).
.../spec.yaml: line 3: field name "first-name" is not a valid identifier.
.../spec.yaml: line 4: duplicate field "a".
.../spec.yaml: line 3: list type must have exactly one element type, e.g. [int].
.../spec.yaml: line 2: record must have at least one field.
.../spec.yaml: input must be a mapping of parameter names to types, got int.
.../spec.yaml: options.targets: unknown target "java" (known: [go rust c]).
.../spec.yaml: yaml: unmarshal errors:
  line 4: field option not found in type project.Spec.
```

The last one is an unknown key (`option` instead of `options`).

## Contradictions

Two examples contradict each other when they have the same input but
different outputs. No function can produce both, so the search could never
succeed; validation reports them instead.

Values are compared after normalising: key order in objects does not matter,
and for `float` values `20`, `20.0` and `2e1` are equal. Both splits are
compared with each other, so a holdout example can contradict a training
example. Identical duplicates (same input, same output) are allowed.
`options.float_tolerance` is not applied here: `0.1` and `0.1000001` are
different outputs.

## Splits: train and holdout

`train` examples are what the search fits. `holdout` examples are kept out
of the search and used afterwards to check the result.

A program can match every training example and still be the wrong
function. With `age` as input and only adults in the training data,
`isAdult = true` fits perfectly. Holdout examples the search has never seen
catch that kind of overfitting. `synth data validate` warns when there are
none.

To fill the holdout split, use `--split holdout` with `data add` or
`data import`, or let `data import --holdout 0.2` pick a random fifth of an
import. The choice depends only on the number of examples, the fraction and
`--seed`, so it is the same on every machine.

## Import formats

[`synth data import`](cli/synth_data_import.md) reads three kinds of source.
All of them are checked completely before anything is written.

**Two folders** (`--inputs DIR --outputs DIR`): `*.json` files paired by
name. The name becomes the example name, or a number if it is not a valid
name. Files without a partner are skipped with a warning.

**JSONL** (`.jsonl` or `.ndjson`): one example per line.

```text
{"input": {"first": "John", "last": "McCarthy", "age": 84}, "output": {"fullName": "John McCarthy", "isAdult": true}}
```

**CSV** (`.csv`): only for specs whose input parameters are all scalars and
whose output is a scalar or a record of scalars. The header has one column
per parameter, plus `out` for a scalar output or `out.<field>` per output
field, in any order:

```text
first,last,age,out.fullName,out.isAdult
Grace,Hopper,85,Grace Hopper,true
```

Bools may be written `true`/`false` or `1`/`0`. String cells are taken
exactly as written, including spaces. A byte order mark at the start of a
JSONL or CSV file is ignored, so files saved by Excel or Notepad work. For
other specs the error says so:

```text
CSV import needs scalar input parameters, but "customer" is {name: string} (use JSONL or directories instead).
```
